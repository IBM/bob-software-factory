Build a simple, visual "software factory" in this repo using
subagents, and markdown files. Keep it small: a viewer should understand the whole
thing in a few minutes. Inspect the repo first so the agents know its language,
test command, and conventions.

## The orchestrator

The factory is one skill, /factory. Whichever Bob session runs it becomes
the orchestrator: it runs the loop below, spawns every agent, and is the only
writer of factory/board.json.

## Rules
- Agents get context from files, not the conversation, and write only their own file.
- Each review starts with VERDICT: PASS or CHANGES; decision.md starts with
  APPROVE or ESCALATE.
- The builder works and commits on a feature branch (factory/<job-id>) and tests
  against the spec's acceptance criteria.
- WAIT FOR ALL: a review round is done only when every reviewer's file exists in
  the round folder. Never resume the builder mid-round.
- Spawn the builder with a name (builder-<job-id>) and resume that same builder
  with SendMessage for each new round, pointing it at the round folder.

## Dashboard
One self-contained HTML file, served with `python3 -m http.server` from factory/.
Jobs are cards moving across the loop's stages. Each review round shows as a row
of reviewer chips that fill in as verdicts land. needs-human jobs stand out. Click
a card to read its markdown files. Clean and minimal.
## The Orchestrator (/factory)

Whichever Bob session runs /factory becomes the orchestrator.
It runs the continuous assembly cycle:

1. Feature Request: Allocates Job ID (e.g., jobs/003-rate-limiting).
2. Spec Writer Bob: Spawns spec-writer subagent -> writes spec.md.
3. Builder Bob: Spawns builder-<job-id> -> creates branch factory/<job-id>, implements, tests, writes build.md.
4. 4 Parallel Reviews:
   ├─ reviewer-security -> round-N/review-security.md
   ├─ reviewer-ux       -> round-N/review-ux.md
   ├─ reviewer-ui       -> round-N/review-ui.md
   └─ reviewer-code     -> round-N/review-code.md
5. WAIT FOR ALL: Barrier sync until all 4 review files exist.
6. Verdict Check:
   ├─ Any "CHANGES" & round <= 2: Resume builder via SendMessage with feedback.
   └─ All "PASS": Spawn approver -> writes decision.md (APPROVE or ESCALATE).
## Factory Execution Rules

• File-Isolated Context: Agents get context from durable disk files, never chat memory.
• Single-File Writers: Each subagent writes only its designated markdown file.
• Deterministic Verdicts:
  - Reviews start with VERDICT: PASS or VERDICT: CHANGES
  - Decisions start with APPROVE or ESCALATE
• Isolated Git Branching: The builder works and commits exclusively on factory/<job-id>.
• Barrier Synchronization: Never resume builder mid-round. Wait for all 4 review files.
• Resumable Builder: Spawn builder with name builder-<job-id> and resume using SendMessage.

.bob/skills/factory/SKILL.md
The brain of the factory. Orchestrator instructions that define the state loop, agent dispatch rules, board.json writing permissions, and CLI command handlers. 
---
name: factory
description: Orchestrates an autonomous multi-agent software factory with parallel reviews and durable markdown state.
---
# Factory Orchestrator

1. Inspect the repo to discover package manager, test scripts, and coding style.
2. Initialize or load factory/board.json.
3. For each job:
   - Spawn spec-writer -> factory/jobs//spec.md
   - Spawn builder (builder-) -> creates branch, writes code & build.md
   - Concurrently spawn 4 reviewers (security, ux, ui, code) into round-N/
   - WAIT FOR ALL 4 review files.
   - If any CHANGES and round <= 2: SendMessage to builder- and repeat.
   - Spawn approver -> factory/jobs//decision.md
   - If APPROVE: merge branch to main; If ESCALATE: mark needs-human.

Engineering Discipline

Factory Rules & Principles

Why this design produces reliable, verifiable code without hallucinated loop drift or context window exhaustion.

📁

File-Isolated Context

Subagents never rely on ephemeral conversation memory. Every input is read from disk (spec.md, git diff), and every verdict is written to its own designated markdown file.

🛡️

Deterministic Verdicts

Every review file strictly begins with VERDICT: PASS or VERDICT: CHANGES. decision.md begins with APPROVE or ESCALATE. No ambiguous summaries.

🛑

Strict Barrier Synchronization

WAIT FOR ALL: The orchestrator will never resume the builder mid-round. A round is only closed when all 4 review files (Security, UX, UI, Code) exist on disk.

🔄

Resumable Subagents

The builder is spawned as builder-<job-id> and resumed with SendMessage pointing to the new review round folder, preserving its local branch context.

👥

Human-in-the-Loop Safeguard

If reviewers request changes after 2 rounds, or if an architectural conflict arises, the job automatically routes to needs-human on the dashboard for approval or rework.

🌿

Isolated Feature Branches

Builders work strictly on factory/<job-id> branches. The main branch remains protected and production-ready until final approval.
